## Approach

A Node script, `scripts/build-copilot-skills.mjs`, reads the 8 `.claude/skills/kopiyka-*/SKILL.md` files and the 4
`.claude/agents/*.md` files, and writes `.github/skills/kopiyka-*/SKILL.md` and `.github/agents/*.agent.md`. It formats
what it writes with the repo's Prettier (already a root devDependency), so `yarn format:check` and `yarn skills:check`
can't disagree. `yarn skills:check` runs the same build in memory and fails, naming the files, when the committed
copies differ. CI's `check` job runs it, so Deploy (which calls `ci.yml`) does too.

Copilot wording that is the same everywhere is a short substitution list in the script. Wording that differs in one
place is marked in the source file. How each mark reaches Claude was checked on Claude Code 2.1.332, the installed
version (see _How Claude Code reads the marks_):

- **Body text only Claude gets**: `<!-- claude -->…<!-- /claude -->`. The script drops it from Copilot's copy. Claude
  reads its own text plus two inert comments. The block can sit inside a line. For whole lines, put the opening
  marker at the end of the previous line (`…opinion.<!-- claude -->`), so dropping it leaves no blank line (a blank
  line inside a list would make Prettier space the whole list out).
- **Body text only Copilot gets**: a placeholder `<!-- copilot: <id> -->` in the body, with the text kept as YAML
  comment lines in the same file's front matter:
  `# copilot text <id>:` followed by `# | <line>` lines (`# |` for an empty line). The script puts the text in place of
  the placeholder exactly as written, so continuation lines carry their own list indent. When Claude loads the skill, it
  sees the placeholder comment but not the text. A raw Read of the file (for example CLAUDE.md's "read conventions"
  line) does show the labelled `# copilot text` lines.
- **Front matter only Copilot gets**: a `# copilot: <key>: <value>` line. The script removes the `# copilot: ` prefix in
  Copilot's copy (`argument-hint`, `disable-model-invocation` for the two orchestrators).
- **Agents**: Copilot's front matter is built from Claude's. `name` and `description` are copied, and `tools` is
  mapped (`Read`→`read`, `Grep`/`Glob`→`search`, `Write`/`Edit`→`edit`, `Bash`→`execute`, `WebFetch`→`web`, with
  duplicates removed and listed in the order read, search, edit, execute, web). `skills` becomes a flow list.
  `disallowedTools`, `color` and `effort` are dropped. The "Before anything else, read `.github/skills/<s>/SKILL.md`
  and … in full and apply them. They are the rules this role works by." line is built from `skills`.
- **Header**: the generated file's second line, inside the front matter, is
  `# Generated by yarn skills:build from <source>. Edit that file, not this one.` The first line has to stay `---`,
  because both tools only read front matter that starts on line 1 (see Open questions).

The brief's example, `<!-- copilot -->…<!-- /copilot -->` in the body, is not used. This is a deliberate departure:
Claude Code passes HTML comments in a skill or agent body to the model as they are, so Copilot text in a body comment
would show to Claude (AC5).
A prototype of this script, run in a scratch copy of the sources marked this way, reproduced all 12 of today's
`.github` files. The only differences were the header line, whitespace, and the one stale conventions line listed
below. The marked sources passed `prettier --check`, and with the marks removed they were byte-equal to today's
(kopiyka-hos differs only by the two blank lines around its placeholder).

Alternative considered: keep all Copilot wording in the script, as `from → to` pairs anchored on Claude's text, with no
marks in `.claude` at all. Claude would read exactly today's files. It lost because it copies Claude sentences into the
script as anchors, and the brief wants the Copilot text to live in the source file. A neutral `skills-src/` (the
brief's open question) lost too: Claude Code loads only `.claude/skills` and `.claude/agents`, and skills-sync edits
`.claude`, so `.claude` would have to be generated as well.

### How Claude Code reads the marks (evidence)

- Docs, https://code.claude.com/docs/en/skills: "Claude Code ignores a field it doesn't recognize without reporting an
  error"; front matter is read "only when the opening `---` is the file's first line"; "If the YAML between the markers
  doesn't parse, the skill still loads with no fields set"; preloaded skills: "the full skill content is injected at
  startup". The page says nothing about HTML comments.
- Docs, https://code.claude.com/docs/en/memory: "Block-level HTML comments … in CLAUDE.md files are stripped". This
  applies to CLAUDE.md only. In the 2.1.332 binary, the stripping function (`aHe`) is called only from the
  CLAUDE.md/memory loaders.
- Probe on 2.1.332 in a scratch project outside the repo: a skill with `# copilot: …` YAML comment lines in its front
  matter, and `<!-- … -->` comments in its body (block, inline and fenced), run with `claude -p "/probe …"`. The session
  transcript's injected skill message held the body with **every** HTML comment verbatim and **no** front matter. The
  skill listing still showed its `description`, so the front matter with comments parsed, and the commented
  `disable-model-invocation` had no effect. An agent body run with `claude -p --agent probe-agent` also kept its HTML
  comments. So: front matter (and the YAML comments in it) never reaches the model, and body comments always do.
- Copilot: `.github/agents/*.agent.md` takes `tools` aliases `execute, read, edit, search, agent, web, todo` and
  `skills` as an array (https://code.visualstudio.com/docs/agents/reference/custom-agent-file-reference). SKILL.md takes
  `argument-hint` and `disable-model-invocation`, and `name` must match the folder
  (https://code.visualstudio.com/docs/copilot/customization/agent-skills). Neither page says how HTML comments in the
  body are handled. That doesn't matter here, because Copilot's copies hold no marks.

- Tooling: `scripts/build-copilot-skills.mjs` (Node 24 ESM, imports `prettier` and `node:fs`/`node:path`).
  - `yarn skills:build` (`node scripts/build-copilot-skills.mjs`): writes the 12 files, deletes an orphan generated
    file (a `.github/skills/kopiyka-*/SKILL.md` from slice 1, or a `.github/agents/*.agent.md` from slice 2, with no

    `wrote N files`, exits 0.
  - `yarn skills:check` (`… --check`): writes nothing. Exits 0 with `Copilot copies are up to date.`, or exits 1 with
    `Out of date, run yarn skills:build:` and one repo-relative path per line (orphans included).
  - Either mode exits 1 with `<source path>: <reason>` when: a placeholder names an unknown text, a text is never used,
    a `claude` marker is unbalanced, a substitution matches nothing, an agent names an unmapped tool or a front matter
    key outside `name, description, tools, disallowedTools, skills, color, effort`.
  - Reads only `.claude/skills/kopiyka-*/SKILL.md` and `.claude/agents/*.md`. Writes only `.github/skills/kopiyka-*/SKILL.md`
    and `.github/agents/*.agent.md`. Never touches the vendored skill symlinks (`.github/skills/<vendored>` →
    `.claude/skills/…`) or the symlinked kopiyka support files (`kopiyka-refactoring/scripts/find-short-names.sh`,
    `kopiyka-store-audit/{scripts,references}/*`).
- Source format: `<!-- claude -->…<!-- /claude -->`, `<!-- copilot: <id> -->`, `# copilot: <line>`,
  `# copilot text <id>:` + `# | <line>`, as in Approach. Ids are `[a-z-]+`, unique per file.
- Reuses: Prettier's `resolveConfig` + `format` with `.prettierrc.json` (no `.prettierignore` change: generated files
  stay checked, and they already are Prettier output); the existing CI `check` job, which `deploy.yml` reuses via

## Not doing (YAGNI)

- Generating `CLAUDE.md`/`AGENTS.md`, the vendored skills or the kopiyka support files (out of scope; already links).
- A root test runner or unit tests for the script. Its only input is the 12 real files, which `skills:check` runs over
  on every CI build. The error paths are checked by hand in slices 1–2. `scripts/` is outside every workspace, so
  `yarn lint` and `yarn typecheck` don't cover the script either; only Prettier does.
- A pre-commit hook, or adding `skills:check` to the four local gates. The brief asks for CI only.
- Changing skills-sync (`.claude/skills-sync.json`). It keeps editing `.claude` only.
- Any wording change to a skill or agent, apart from the one stale Copilot line.

## Risks

- Copilot's front matter reader rejects a YAML comment as the first front matter line, so skills or agents stop
  listing. Disproved by the user's **Open Customizations** check after slice 2. Fallback: move the header to the first
  body line as an HTML comment.
- A `copilot` text's indentation breaks a list in Copilot's copy. Caught by slice 1's word-diff and by Prettier (a
  broken list reflows visibly).
- A future Claude Code passes front matter to the model, so `# copilot text` lines become visible. The slice 2 (b)/(c)
  checks show it today. Recheck when 111 runs `/kopiyka-hos`.
- An edit inside a `<!-- claude -->` block (by hand or by skills-sync) leaves its Copilot text stale, and no check can
  see that. Mitigated by slice 4's `docs/copilot.md` rule: when you change a `claude` block, update its `copilot` text.
- Claude reads a marked source with the Read tool (CLAUDE.md:8 for conventions) and sees the `# copilot text`
  front-matter lines. Accepted as harmless: they are labelled Copilot-only, and conventions holds only three short ones
  (browser, deny-list, if-installed). Any in-file mechanism, including the brief's own `<!-- copilot -->` example, has
  the same exposure.
